What poll actually does, in order

  1. Ask how long it may sleep. uv_backend_timeout() runs the six-rule cascade in panel 1 and returns a millisecond count, 0, or -1 for "forever".
  2. Call epoll_wait() with that timeout — on the main thread, watching every registered fd plus libuv's own async handle. This is where an idle Node process spends its life at ~0% CPU.
  3. Wake. Either the timeout expired, or the kernel marked an fd ready, or a thread-pool worker wrote a byte to the async pipe. The clock advances to the moment of waking.
  4. Harvest the ready set into a batch. Every fd the kernel reported, plus every completed thread-pool request, becomes a queued callback (panel 3).
  5. Dispatch the batch, one callback at a time. Push the frame, run it to completion, pop. Two I/O callbacks are never on the stack together.
  6. Drain nextTick, then microtasks — fully — after each one. Only then does the next I/O callback start.
  7. Leave. Once the batch is empty, poll is done for this lap. It does not block a second time; it walks on to check, then close, then round to timers.

Three things that surprise people

  • Poll does not loop back per callback. It stays in the phase until the harvested batch is finished, then moves on. New I/O completing mid-batch needs a fresh epoll_wait — next lap.
  • A pending setImmediate stops poll from sleeping at all. Node keeps an active idle handle while immediates are queued, which trips rule 3 and forces the timeout to 0.
  • Pool completions land in poll too. The worker did the blocking work but could not run your JavaScript. It signalled through the async handle; your callback still runs here, on the main thread.

Why the clock is frozen for the whole lap

uv_run() samples the clock exactly once per iteration, at the very top:

while (r != 0 && loop->stop_flag == 0) {
  uv__update_time(loop);      /* loop->time = now, ONCE */
  uv__run_timers(loop);       /* compared against loop->time */
  ...
  uv__io_poll(loop, timeout);
  ...
}

And uv_timer_start() computes a deadline against that same frozen value, not against the wall clock:

handle->timeout = loop->time + timeout;

Node clamps any delay below 1 up to 1, so the earliest deadline you can create during a lap is loop->time + 1. The timers phase drains while handle->timeout <= loop->time — and frozen + 1 > frozen is always true. A timer created during a lap can never be due on that lap. That is arithmetic, not policy.

What the frozen clock buys you

The timers phase is a for(;;) loop that re-reads the heap minimum on every pass — so a timer callback feeds the very heap being drained:

for (;;) {
  heap_node = heap_min(timer_heap(loop));
  if (heap_node == NULL) break;
  handle = container_of(heap_node, uv_timer_t, node.heap);
  if (handle->timeout > loop->time) break;   /* not due — stop */
  uv_timer_stop(handle);
  uv_timer_again(handle);
  handle->timer_cb(handle);
}

If loop->time were re-read from the wall clock on each pass, a recursive setTimeout(fn, 0) inside a timer callback would become due again the moment 1 ms of real time had elapsed — and callbacks easily take that long. The phase would keep finding a due timer and never break. Freezing the clock makes that impossible by construction.

Note that two independent things defer a timer created mid-lap. Ordering is the obvious one: timers is the first phase, so from a poll callback it has already run. The arithmetic above is what covers the case ordering does not — a timer created inside a timer callback, while uv__run_timers is still looping.

Which is why setTimeout(fn, 0) does not mean “as soon as possible”. It means no earlier than the next iteration — a floor, not a target. That is the whole reason setImmediate exists: it trips rule 3, poll does not sleep, and check runs it on the current lap.

What server.listen(3000) actually does

  1. Node creates a TCP handle and calls bind() to claim the port, then listen() to tell the kernel to start queueing connections for it.
  2. The listening fd is registered with the loop's poll set — one more descriptor for the epoll_wait() that poll already calls. No thread is used and nothing is queued. This is the single most common misreading of Node: an idle server is not "waiting" in any thread of its own.
  3. The handle is referenced, so uv__has_active_handles() stays true forever. Rule 2 can never fire again — which is precisely why a server process does not exit when the script ends.
  4. With no timers pending, the cascade falls to rule 7. epoll_wait blocks indefinitely, at ~0% CPU. That is a server at rest, and it is where the process spends almost all of its life.
  5. A client connects. The kernel finishes the handshake, puts the connection on that socket's accept queue and marks the fd readable, which returns epoll_wait immediately.
  6. In the poll phase libuv calls accept(), wraps the new fd in its own handle, and runs your connection callback — on the main thread, like every other I/O callback. The listening socket is untouched and still in the set.

Two consequences worth holding onto. Everything a connection handler schedules obeys the same rules as any other poll callback — a setImmediate in it beats a setTimeout(fn, 0) beside it, every time. And server.unref() flips point 3: the handle stops counting as referenced, so the loop is free to exit while the server is still technically listening.

The batch is bounded

libuv reads at most a fixed number of events per epoll_wait call and will only re-poll a bounded number of times within one iteration. A firehose of ready sockets therefore cannot keep poll from ever reaching check and close. What can stall the loop is your own code: one slow synchronous callback, or a nextTick/promise chain that keeps refilling itself.
